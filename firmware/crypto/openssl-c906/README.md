# NanoKVM OpenSSL patches

Patches apply in filename order to the SHA-256-pinned OpenSSL release in
`platform/sources.lock`, with zero fuzz. The runtime records every patch digest
in `/usr/share/nanokvm/openssl/source.json`. Each algorithm has its own patch
and pull request; upstream upgrades must requalify the affected algorithms.

## ChaCha20

`0001-chacha20-c906.patch` adds our C906 five-block implementation to OpenSSL's
existing RISC-V primitive dispatch. The default provider keeps its existing
ChaCha20/Poly1305, TLS, buffering, tag verification and counter-limit handling.
No ENGINE or cryptodev interface is involved.

The GNU ABI assembly is generated from
`firmware/cpu/go-crypto-c906/gen_chacha_linux.py`, which also supplies Linux's
ChaCha implementation. Its four vector lanes and fifth scalar block share the
round construction with the separate Go generator. The GNU version preserves
the C callee-saved registers, takes a 16-word state and round count, and wipes
its stack keystream. The Go implementation uses a different ABI and buffer
wrapper; its timings are not OpenSSL measurements.

From `OSSL_CHACHA_C906_MIN_BYTES` (129 bytes, three blocks) the vector code
runs; a remainder of three or more blocks after the whole groups takes one
group padded to 320 bytes. Shorter inputs and remainders use the scalar
CRYPTOGAMS ChaCha20 (`chacha-scalar.S`, generated by
`generate-chacha-scalar.py` from `chacha-riscv.pl` at a pinned commit, with
the Zbb rotations replaced by XTheadBb `th.srriw`). The stock C code and the
Zbb/RVV 1.0 kernels are no longer used: the C906 has neither extension.

Stand, ns per call, best of five (`bench-chacha.c`, 2026-11-10):

| Bytes | upstream C | CRYPTOGAMS scalar | one padded vector group |
|---|---|---|---|
| 16 | 1403 | 1282 | 3191 |
| 64 | 1779 | 1227 | 3325 |
| 128 | 3519 | 2469 | 3427 |
| 192 | 5217 | 3703 | 3508 |
| 319 | 8659 | 6610 | 3755 |

`openssl speed -elapsed -evp`, MB/s, before -> after: chacha20 64 B 30.7 ->
40.8, 256 B 34.8 -> 58.1, 1400 B 81 -> 87; chacha20-poly1305 64 B 24.3 -> 30.2,
256 B 28.4 -> 42.6, 1400 B 61 -> 63; 8 KiB unchanged.

GHASH uses 8-bit tables, see "GHASH" below. CRYPTOGAMS SHA-512 (33.2
MB/s) and SHA-256 (22.1) were within noise of OpenSSL's C SHA-512 (32.7)
and our C906 SHA-256 (21.8), so neither replaced them.

There is no run-time check: NanoKVM OS runs only on the SG2002, and its kernel
keeps the vector unit on for every user thread
(`platform/kernel/0078-riscv-user-vector-always-on.patch`: no thread can turn
it off or start a program with it off). The ChaCha20, GHASH and Poly1305 paths
therefore make no system call and need no environment variable, so they work
in every process, including those under seccomp filters (OpenSSH's
pre-authentication sandbox). Earlier versions asked `PR_RISCV_V_GET_CONTROL`
on every call and needed the opt-in `NANOKVM_OPENSSL_CHACHA20=auto`, which only
the image downloader's curl set, and a startup `riscv_hwprobe` of the T-Head
vendor key. CI does not run this library: it checks the patches, the
generated assembly and the arithmetic of the C906 kernels in separate test
programs.

`NKOS_CHACHA_TEST` adds an atomic counter at the actual assembly entry and an
accessor for a private test-library export map. Production builds omit both
and retain the original 5808 dynamic definitions.

The assembly is used under its BSD-3-Clause option; the runtime carries the
BSD license alongside OpenSSL's Apache-2.0 license. The new C glue is Apache-2.0.
Generate/verify with the same binutils used to build the firmware:

```sh
python3 firmware/crypto/openssl-c906/generate-chacha.py \
  --binutils /path/to/riscv64-buildroot-linux-musl- --check
```

## GHASH

`0010-ghash-c906.patch` replaces the 4-bit table GHASH (26 MB/s on the C906)
by the 8-bit table code of `firmware/cpu/go-crypto-c906/gen_ghash_table.py`
(two tables of 4 KiB per key, 114 MB/s; not constant-time, like the 4-bit
table). Both the block function and the single multiplication of
`CRYPTO_gcm128_*` use it.

Building the tables costs about 9 us, as much as hashing 300 bytes with the
4-bit table. A key therefore hashes its first 512 bytes with the 4-bit table
and builds the tables after that. They are the last member of
`GCM128_CONTEXT`, and `CRYPTO_gcm128_init` zeroes only the members before
them.

TLS-like records (one key, a new IV, 13 bytes of AAD and a tag per record;
`openssl speed -aead` sets the key again for every record and does not show
this), time to encrypt one record on the SG2002, before -> after, together
with the function order below: AES-128-GCM 256 B 24.0 -> 17.0 us, 1400 B
80 -> 44 us, 16 KiB 568 -> 331 us; AES-256-GCM 1400 B 82 -> 46 us. Records
that set the key every time are about 1 us slower up to 256 bytes (the
larger context).

## Function order

The C906 has a 2-way 32 KiB instruction cache and no L2 cache. OpenSSL's hot
functions are spread over a 2 MiB text segment, and the ones a TLS record
calls evict each other depending on where unrelated code happens to move
them: the same 773 million instructions of a ChaCha20-Poly1305 record
benchmark took 1.16 or 1.30 billion cycles in two builds that differed only
in the GHASH code, with 1.2 and 2.0 million instruction-cache misses (about
170 cycles each).

`scripts/build-openssl.py` therefore compiles with `-ffunction-sections` and
links with `--section-ordering-file=hot-sections.ld`. The file lists the
assembly kernels and about 530 C functions by workload class, so that the
code one workload touches is contiguous: functions common to several classes,
ChaCha20-Poly1305 records, AES-GCM records, SHA-256, the other hashes, TLS
connections. A single block ordered by call count alone was worse than this.
After the build the script checks that most listed names are still functions
of libcrypto and close together; a new OpenSSL version that renames or inlines
them fails the build instead of silently losing the order.

Measured: ChaCha20-Poly1305 records 256 B 12.3 -> 10.4 us, 1400 B 28.5 ->
24.6 us (0.5-1.0 million misses instead of 1.2); `openssl speed -evp`, 16 /
64 / 1024 bytes, MB/s: sha1 2.5 / 4.6 / 34.9 -> 4.8 / 10.3 / 47.3, md5
3.9 / 14.0 / 71.5 -> 4.7 / 14.5 / 73, sha256 and sha512 unchanged. A 16-byte
SHA-1 digest takes 1-4 instruction-cache misses instead of 13-21. The address
of libc relative to libcrypto changes from run to run and still moves a
record by about 0.5 us.

The order is measured, not proven. The build also passes
`-falign-functions=4 -falign-jumps=4 -falign-loops=4 -falign-labels=4`
(`scripts/nanokvm_cpu_profile.py`): with the same list and without these
flags a 16-byte SHA-256 digest (4300 instructions over about a hundred
functions) took 27-31 instruction-cache misses instead of 10 and was a third
slower than before the change, while records were unaffected. After a change
of OpenSSL, of the patches or of the flags, measure records and small digests
again.

To regenerate `hot-sections.ld`: build OpenSSL with `-finstrument-functions`
and link `hot-sections/callcount.c` into it (it counts calls per function and
writes "module offset count" lines at exit), run the workloads on a device,
turn each output into "calls symbol" lines with `nm`, and run
`hot-sections/mkorder.py OUT` in the directory holding `chacha.txt`,
`gcm.txt` (records), `hash1.txt`... (`openssl speed` of sha256, sha1, sha512,
HMAC, md5 at 64 and 1024 bytes) and `tls*.txt` (`openssl s_time`).

## NIST curves

The build enables `enable-ec_nistp_64_gcc_128`: OpenSSL has no RISC-V
assembly for P-256 and otherwise uses its generic big-number code. On the
SG2002: ECDSA P-256 sign 13.8 -> 1.8 ms, verify 11.0 -> 3.8 ms; ECDH P-256
13.0 -> 2.5 ms; ECDH P-384 27.2 -> 6.8 ms. Full TLS 1.3 handshakes per second
with client and server both on the device (`openssl s_time -new`): ECDSA
certificate with X25519 22 -> 36, with P-256 10.8 -> 29; RSA-2048 certificate
with X25519 20 -> 20 (the 31 ms RSA signature), with P-256 10.4 -> 17.6.

## Direct SG2002 transport

`0002-hwcrypto-transport.patch` adds the shared private ioctl client for subsequent
per-algorithm patches. On its own it selects no hardware algorithm and changes
no EVP result. It is compiled only for RISC-V64, outside the FIPS module. The
module ships in the same image, so there is no ABI or capability probe; a
process keeps one descriptor for all threads. EIO/ETIMEDOUT from a poisoned or
hung engine still fall back to software.

## SHA-224/256

`0003-sha256-dma.patch` uses the shared direct transport for full compression
chunks. OpenSSL owns streaming, padding, digest lengths and software fallback.
The FIPS module is excluded. The remainder goes straight to the scalar C906
kernel; the Zvknh check of the stock dispatch is not compiled for XTheadBb
builds. `tests/test-scalar.py` runs the patched wrapper and scalar assembly on
QEMU's C906 CPU. DMA starts at 1 KiB (wall-clock break-even).

The scalar kernels come from `firmware/cpu/go-crypto-c906/gen_sha2_c906.py`:
SHA-256 (`sha256-c906.S`) and SHA-512 (`sha512-c906.S`, also SHA-384 and
SHA-512/256). Rounds 0 to 15 are emitted once and one body of 16 rounds runs
three (SHA-256) or four (SHA-512) times, 4.5 KiB of code each. The previous
SHA-256, unrolled from the Go core, was 9 KiB, more than a quarter of the
instruction cache. A loaded value is used no sooner than two instructions
later; w[i-1], w[i-2] and w[i-16] stay in registers. On the SG2002: SHA-256
2451 ns per block against 2610 unrolled (26.1 against 24.5 MB/s); SHA-512
3103 ns per block against 4240 for C (41.2 against 30.2 MB/s in the same test
program; OpenSSL's own C build did 36.6). `openssl speed -evp`, MB/s at 16 /
64 / 1024 / 16384 bytes, before -> after: sha256 2.4 / 6.9 / 32.5 / 156 ->
2.9 / 8.0 / 37-43 / 161; sha512 1.9 / 7.6 / 28.9 / 36.6 -> 2.0 / 8.1 / 31.4 /
40.6. The generator checks itself against a plain implementation anchored to
hashlib.

## AES

`0005-aes-c906.patch` separately optimizes the existing scalar AES table lookups
with XTheadBb byte extraction and scaled XTheadMemIdx loads. The original
RISC-V/FIPS assembly remains the fallback. It changes neither tables nor key
schedules.

`0005-aes-dma.patch` adds ECB/CBC/CTR and the AES-CTR primitive used by GCM.
OpenSSL retains streaming, padding, GHASH, authentication and TLS handling.
The shared block helper commits only completed chunks and supports separate
full-width and GCM counters. GCM installs the AES-CTR callback for every record;
below the 512-byte DMA minimum it encrypts one AES block per call with 64-bit XOR
and a register counter.

From 4 KiB, a GCM update hands its whole blocks to the driver's
`HWCRYPTO_GCM` ioctl instead (the driver's ABI header is copied into
`0002`). The driver runs AES-CTR on the engine in 4 KiB chunks and, while
each chunk runs, the kernel's C906 GHASH over the previous chunk's
ciphertext (encryption) or the same chunk's input (decryption), as its
`gcm(aes)` does. The request carries the key, H, the GHASH accumulator Xi and
the counter block, and the driver returns Xi and the counter advanced over the
completed prefix. As for `AES_GCM_ASM`, `CRYPTO_gcm128` first finishes the
associated data and any partial block, and keeps the lengths, the last partial
block and the tag. If a call fails or stops early, the rest takes the CTR
callback path. One call costs about 2.4 us more than `HWCRYPTO_RUN`, and
below 4 KiB the overlap does not pay for it: 512 to 1400-byte records were
about 10 us slower with the limit at 512 bytes.

Stand (NanoKVM PCIe), `openssl speed -elapsed -evp` with one key (`-decrypt`
for decryption), application stopped, two alternating rounds, MB/s, without ->
with `HWCRYPTO_GCM`; 1408 bytes take the unchanged path:

| | 1408 B | 4096 B | 16384 B |
| --- | ---: | ---: | ---: |
| AES-128-GCM encrypt | 22-25 -> 24 | 35-37 -> 45 | 46-47 -> 64-65 |
| AES-128-GCM decrypt | 22-24 -> 22-23 | 37-38 -> 45 | 46-49 -> 64 |
| AES-256-GCM encrypt | 23-25 -> 22-24 | 32-36 -> 42 | 44-45 -> 63 |
| AES-256-GCM decrypt | 22-23 -> 21 | 35-37 -> 45-46 | 45-47 -> 64 |

TLS-like records (new IV, 13 bytes of associated data, tag; one key), time per
record to encrypt / decrypt in us, AES-128-GCM: 4096 bytes 98 / 95 -> 96 / 85,
16 KiB 344 / 341 -> 272 / 259. The output of every size is identical.

The engine is shared with the server's SRTP. Latency of SRTP-sized engine
requests (1188 bytes, 1250 a second, application running) while
`openssl speed` runs 16 KiB records, two runs each of an encrypting and a
decrypting load, in us:

| | p50 | p90 | p99 | p99.9 |
| --- | ---: | ---: | ---: | ---: |
| no load | 18 | 48-50 | 62-66 | 125-206 |
| load without `HWCRYPTO_GCM` | 20-21 | 21-61 | 22-78 | 122-219 |
| load with `HWCRYPTO_GCM` | 20-21 | 22-61 | 57-115 | 125-165 |

A WebRTC session in Chrome showed 60 frames a second under either load, with
52 to 55 frames in 8 s dropped by the browser without and 53 to 73 with the
ioctl (none when idle): the load competes for the CPU either way. The load
itself ran at 21 MB/s without and 28 MB/s with it beside that session.

OpenVPN data channel offload shares the engine from softirq. With the
application stopped, received / sent in Mbit/s: AES-256-GCM 87 / 77 with the
previous driver and 86 / 75 with this one; ChaCha20-Poly1305 90 / 88 both.
With a 16 KiB AES-GCM encryption loop beside the tunnel: AES-256-GCM 81 / 40
whether the loop uses the ioctl or not, the loop at 20.8 MB/s without and
29.9 MB/s with it. The digest of 24544 AES-GCM operations through the ioctl
path (split updates, IV and key lengths, tampered tags) stays the one of the
previous library, also while the tunnel is loaded.

A driver from before `HWCRYPTO_GCM` answers ENOTTY: the module of the running
kernel is older than the library after an update, until the reboot. The
library remembers that and keeps the AES-CTR path (same speed and output as
before).

`0004-sha1-dma.patch` sends the whole blocks of SHA-1 to the engine as
`0003` does for SHA-256, from 2 KiB (at 1 KiB the C code is faster: 46 MB/s
against 34). Both hand the driver up to 64 KiB per request. `openssl speed
-elapsed`, the application stopped, MB/s, before -> after:

| | 1024 B | 2048 B | 4096 B | 8192 B | 16 KiB | 64 KiB |
|---|---|---|---|---|---|---|
| SHA-1 | 46 -> 46 | 52 -> 58 | 56 -> 97 | 58 -> 142 | 59 -> 189 | 57 -> 196 |
| SHA-256 | 34 -> 33 | 56 -> 63 | 102 -> 104 | 127 -> 159 | 154 -> 200 | 160 -> 220 |

The AES PR is based directly on the SHA-256 patch. DES, TDES and SM4
OpenSSL offloads are not included. The AES helper rejects other algorithm IDs,
and the legacy provider does not link the SG2002 transport.

## Poly1305

OpenSSL 3.5 has no RISC-V Poly1305 assembly, so it ran the generic C code.
`0011-poly1305-riscv.patch` adds `crypto/poly1305/asm/poly1305-riscv.pl`
from CRYPTOGAMS (Andy Polyakov, written for OpenSSL's `poly1305_init`,
`poly1305_blocks`, `poly1305_emit` interface), byte for byte the file Linux
7.3.1 builds for `lib/crypto` (SHA-256 `9a75fc04cd61e8fb...`), so OpenSSL
and the kernel run the same Poly1305. It is used under its BSD-3-Clause
option; the runtime carries `CRYPTOGAMS-BSD-3-Clause.txt`. `build.info`
selects it for `riscv64` like the other architectures' assembly; it is
outside the FIPS module, and the dynamic symbol table is unchanged (5808
definitions). The OpenSSL flags include `-mtune=thead-c906`, for which GCC
defines `__riscv_misaligned_fast`, so the word-load input paths are built
(no byte loads in `poly1305-riscv.o`).

Stand, `openssl speed -evp chacha20-poly1305`, best of three, MB/s:

| | 1400 B | 16 KiB |
| --- | ---: | ---: |
| generic Poly1305, C906 ChaCha20 | 50.8 | 56.8 |
| CRYPTOGAMS Poly1305, C906 ChaCha20 | 54.4 | 62.4 |
| generic Poly1305, generic ChaCha20 | 32.4 | 33.4 |
| CRYPTOGAMS Poly1305, generic ChaCha20 | 33.8 | 34.9 |

From the ChaCha20-only rate of the same build, Poly1305 goes from about 163
to about 219 MB/s at 16 KiB (the kernel's copy measures 228). OpenSSL's
`test_poly1305` and an EVP check of 408 AEAD known answers and rejected tags
pass on the device.

### Vector Poly1305

`0012-poly1305-c906.patch` adds the C906 vector Poly1305 that NanoKVM's Go
runtime and kernel use: radix 2^26, four blocks in XTheadVector lanes and
one in scalar registers per group of five. It is
`firmware/cpu/go-crypto-c906/gen_poly1305_vector.py --openssl`, and that
generator executes it against a big-integer Poly1305; see
`firmware/cpu/go-crypto-c906/README.md`.

- **Selection.** As for ChaCha20 and GHASH there is no run-time check (the
  kernel keeps the vector unit on for every user thread, patch 0078):
  `Poly1305_Init` replaces `func.blocks` with `ossl_poly1305_blocks_c906`.
- **Split.** The vector function takes runs of at least eight whole groups
  (640 bytes) with padbit 1. Cryptogams `poly1305_blocks` takes the rest and
  every other call.
- **Context.** The glue converts the Cryptogams context (h0, h1, h2; r0, r1,
  s1) to 26-bit limbs and back, after folding h2 as `poly1305_emit` does.
- **Threshold.** The vector function computes r^2..r^5 on every call, so
  with `EVP_MAC`, a fresh key per message, it overtakes Cryptogams at about
  640 bytes.

Stand, 2026-11-09:
- The vector path produces the same 6000
  tags (lengths to 65 KB, offsets 0-15, update splits, all-ones keys and
  messages) as Cryptogams (measured with the opt-in variable of an earlier
  revision; the code path is the same).
- The 408-case EVP AEAD check passes.

MB/s, Cryptogams -> vector; `EVP_MAC` is three alternating rounds:

| | 1024 B | 1400 B | 4096 B | 16 KiB |
| --- | ---: | ---: | ---: | ---: |
| `EVP_MAC` Poly1305, fresh key | 122-131 -> 126-149 | 126-143 -> 138-168 | 179-180 -> 240-256 | 194-200 -> 294-310 |
| `openssl speed -evp chacha20-poly1305` (vector ChaCha20 in both) | | 62.9-63.3 -> 65.9-66.3 | | 74.0-74.2 -> 85.1-85.7 |

Below 640 bytes the vector function is not called; there the rounds differ
from each other by up to 15%, more than between the two settings.
