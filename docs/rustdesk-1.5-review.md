# RustDesk 1.5.0: база аддона NanoKVM и перенос функций

Проверено 3 октября 2026 года по исходникам фиксированных релизов, а не только по changelog. Текущий пакет после этой работы: **nanokvm-rustdesk 0.2.1-r0**. База используемой части протокола: **RustDesk 1.4.9**. Это отдельный HDMI/HID endpoint, производный от OneKVM, а не полный клиент RustDesk с заменённым номером версии.

## Происхождение и номера версий

- OneKVM: `7a278b5897716786dcc075a167b72f04d5b73766`.
- RustDesk 1.4.9: `6c578292e8ebbbec708b76986ba8c4bc7c509747`; его hbb_common: `7e1c392c62d39c364127307cd408421dd5f8cfb0`.
- RustDesk 1.5.0: `fada664df7a294d1d1a9ca3e7cd3637069122f17`; его hbb_common: `229b904508364c8997aad0fb5af57effac859f60`.

Наследованная строка `1.4.9` сама по себе не доказывала происхождение из этого тега. Поэтому схема проверена отдельно: 120 из 121 проверенной декларации полей структур до текущего изменения имеют соответствующие номера в схеме 1.4.9. Исключение — уже унаследованное поле PunchHoleRequest.switch_code (11), присутствующее в 1.5.0. Это проверка выбранных полей, не доказательство реализации всего upstream. Формулировка интерфейса «RustDesk — база протокола» отражает именно такой статус.

В установленном APK теперь есть `upstream.json` с этими ссылками и версией базы. API читает его из установленного пакета; бинарник встраивает тот же файл. Собственная версия берётся из базы APK и включает ревизию. Старый пакет без метаданных показывает неизвестную базу, а не выдуманную версию. Номера отображаются и в Add-ons, и в управлении расширением.

Источники: [OneKVM на исходном commit](https://github.com/onekvm/onekvm-extension-rustdesk/tree/7a278b5897716786dcc075a167b72f04d5b73766), [RustDesk 1.4.9](https://github.com/rustdesk/rustdesk/tree/6c578292e8ebbbec708b76986ba8c4bc7c509747), [RustDesk 1.5.0](https://github.com/rustdesk/rustdesk/tree/fada664df7a294d1d1a9ca3e7cd3637069122f17).

## Что меняется на проводе

Сравнение двух точных схем показывает преимущественно добавление полей, без изменения используемых номеров HDMI-видео, логина и клавиатуры/мыши. Видео H.264/H.265 сохраняет прежнюю структуру. Перенос message.proto из hbb_common в libs/base — реорганизация исходников, а не новый формат видеопотока.

IdPk перенесён в rendezvous.proto, дополнен подписанным DTLS fingerprint и объявляемой версией KX. PublicKey получает выбранную версию KX. В сигнализацию добавлены SDP offer/answer и IceCandidate, а в KeyExchange — версия и подписанные параметры. Есть также новые сообщения мультиплексированного port forwarding и запрос повторной формы курсора; наш HDMI/HID endpoint этих функций не реализует.

[Схема сообщений 1.5.0](https://github.com/rustdesk/rustdesk/blob/fada664df7a294d1d1a9ca3e7cd3637069122f17/libs/base/protos/message.proto), [схема rendezvous 1.5.0](https://github.com/rustdesk/hbb_common/blob/229b904508364c8997aad0fb5af57effac859f60/protos/rendezvous.proto).

## Приоритеты переноса

| Изменение | Польза для NanoKVM | Решение |
| --- | --- | --- |
| KX v1 | Отдельные ключи на отправку и приём, связь ключей с параметрами handshake | Первый полноценный перенос протокола |
| Ротация временного пароля после входа | Переданный пароль перестаёт оставаться действующим всю сессию | Следом, вместе с правилами переподключения |
| WebRTC | Возможность прямого соединения вместо hbbr relay | Отдельный этап после проверки транспорта на устройстве |
| QoS | Меньше задержка очереди при плохом канале | Адаптировать к общему NanoKVM encoder |
| Dead peer recovery | Быстрее восстановление оборванного соединения | Включить в этап WebRTC; upstream-изменение относится главным образом к контроллеру и KCP/WebRTC |
| HDR, clipboard, file transfer, port-forward mux | В основном функции полноценного desktop client | Для текущего HDMI/HID endpoint не первый приоритет |

### KX v1

1.5.0 согласует версию обмена ключами, выводит разные ключи для двух направлений и связывает их с обеими эфемерными public keys и объявленной/выбранной версией. Сохраняет KX v0 для старых peers. Для WebRTC шифрование выполняет DTLS, поэтому upstream выбирает KX v0 на этом транспорте.

В текущем пакете перенесены **разбор PublicKey.kx_version и отказ от не предложенной версии**. Полный KX v1 ещё не объявляется: подписанный IdPk по-прежнему предлагает v0 отсутствующим полем. Клиент 1.5.0 по своему исходному коду выбирает v0 для такого peer. Менять лишь строку версии на 1.5.0 не нужно.

Следующий перенос требует раздельного хранения send/receive keys, точного воспроизведения upstream derivation, проверки подписанных параметров при защищённой TCP-сигнализации и тестов обмена с настоящими клиентами обеих версий. Совпадения названий алгоритмов недостаточно.

[Изменение KX v1](https://github.com/rustdesk/rustdesk/pull/16326), [реализация upstream криптографии](https://github.com/rustdesk/hbb_common/blob/229b904508364c8997aad0fb5af57effac859f60/src/tcp.rs).

### WebRTC

Это ICE + DTLS + SCTP **data channel для сообщений RustDesk**. Это не переход нашего видео на RTP track и не замена аппаратного encoder. Существующие H.264/H.265 frames можно передавать через новый транспорт без decode/re-encode.

Однако перенос включает answerer, защищённую TCP-сигнализацию SDP/ICE через hbbs, жизненный цикл ICE/DTLS/SCTP, фрагментацию крупных сообщений, ограниченные очереди и fallback на relay. Требуется ID-сервер, умеющий пересылать новые поля и ICE candidates; поддержка именно нашего публичного сервера ещё не проверена. Политики relay/proxy также должны сохраниться.

DTLS fingerprint связывается с подписанным IdPk: одного шифрования канала без проверки peer identity недостаточно. Финальный релиз содержит дополнительные изменения защиты сигнализации и ограничения параллельных answerer setups после исходного WebRTC PR. Поэтому переносить нужно итоговые исходники тега 1.5.0. В них webrtc 0.13 дополнен patch на fork `rustdesk-org/webrtc` commit `49c89bd8d30e6e62e4c1a96cee38fdc11f79ef63`; одного добавления crates.io зависимости недостаточно.

В нашем Go-сервере уже есть Pion WebRTC v4 для браузерного видео (`server/service/stream/webrtc`, версия зависимости в `server/go.mod`). DataChannel API этой библиотеки также используется в локальных тестах DTLS; в рабочем браузерном видеопотоке data channel сейчас не задействован. Поэтому перед добавлением второго WebRTC stack в Rust стоит сравнить две архитектуры: upstream Rust transport и небольшой Go/Pion data-channel bridge с локальным IPC к демону. Второй вариант позволит использовать уже имеющуюся Go-зависимость, но потребует адаптера сигнализации, фрагментации и подписанного fingerprint. Совместимость Pion с протоколом RustDesk здесь ещё не испытана; наличие браузерного WebRTC её не доказывает. Для первого прототипа этот вариант заслуживает проверки.

Оценка осуществимости положительная: RISC-V сам по себе не исключает этот Rust transport. Практическая пригодность на SG2002 пока не установлена. Критерии приёмки: CPU/RSS под видео, ограничение размера сообщений и очередей, отсутствие утечек после повторных reconnect, корректный relay fallback и освобождение HID при обрыве/переходе управления в браузер. Оценка — вывод из архитектуры; измерений WebRTC на нашем устройстве ещё нет.

[WebRTC PR](https://github.com/rustdesk/rustdesk/pull/15684), [итоговый транспорт](https://github.com/rustdesk/hbb_common/blob/229b904508364c8997aad0fb5af57effac859f60/src/webrtc.rs), [patch dependencies релиза](https://github.com/rustdesk/rustdesk/blob/fada664df7a294d1d1a9ca3e7cd3637069122f17/Cargo.toml).

### Пароли, QoS и восстановление

В 1.5.0 временный пароль обновляется при успешной авторизации. Upstream сохраняет недавнюю сессию для reconnect, поэтому простой перенос ротации без session reuse вызовет повторные запросы пароля при сетевых обрывах. У нас сейчас пароль меняется при старте службы или вручную; новая семантика пока не внедрена.

QoS 1.5.0 различает базовую задержку и рост очереди, подтверждает перегрузку несколькими измерениями и управляет bitrate/FPS. У NanoKVM encoder общий с браузером: прямой перенос управления encoder может менять картинку другого зрителя. Нужны согласованная политика владельца и учёт зависимых кадров — простое отбрасывание H.264/H.265 delta frames портит поток.

Upstream recovery ускоряет обнаружение исчезнувшего peer для KCP/WebRTC. Большая часть изменения находится в клиентском io_loop; оно не является готовым исправлением регистрации UDP нашего демона.

[Ротация пароля](https://github.com/rustdesk/rustdesk/pull/16080), [QoS](https://github.com/rustdesk/rustdesk/pull/16082), [Dead peer recovery](https://github.com/rustdesk/rustdesk/pull/16117).

## Что проверено сейчас

25 Rust tests пройдены, 2 сетевых теста помечены ignored. Новые проверки: wire fixtures, закодированные protoc по схеме 1.5.0; сохранение зашифрованного KX v0 handshake и отказ от не предложенного KX v1. Go-тесты проверяют чтение базы из установленного пакета, будущую версию, отсутствие/повреждение metadata и удалённый пакет. Frontend проходит TypeScript/Vite, ESLint и Prettier.

Это не квалификация полного клиента 1.5.0 и не испытание WebRTC. Ранее видео с Windows client 1.4.9 работало через encrypted relay. Полная проверка штатным клиентом 1.5.0 остаётся отдельной задачей перед заявлением его поддержки.
