# NanoKVM OpenSSL patches

Patches apply in filename order to the SHA-256-pinned OpenSSL release in
`platform/sources.lock`, with zero fuzz. The runtime records every patch digest
in `/usr/share/nanokvm/openssl/source.json`. Each algorithm has its own patch;
after an OpenSSL upgrade, test and measure the affected algorithms again.

## ChaCha20

`0001-chacha20-c906.patch` adds our C906 five-block implementation to OpenSSL's
existing RISC-V primitive dispatch. The default provider keeps its existing
ChaCha20/Poly1305, TLS, buffering, tag verification and counter-limit handling.
No ENGINE or cryptodev interface is involved.

The GNU ABI assembly is generated from
`firmware/cpu/go-crypto-c906/gen_chacha_linux.py`, which also supplies Linux's
ChaCha implementation: four vector lanes and a fifth scalar block. It
preserves the C callee-saved registers, takes a 16-word state and round count,
and wipes its stack keystream.

From `OSSL_CHACHA_C906_MIN_BYTES` (129 bytes, three blocks) the vector code
runs; a remainder of three or more blocks after the whole groups takes one
group padded to 320 bytes. Shorter inputs and remainders use the scalar
CRYPTOGAMS ChaCha20 (`chacha-scalar.S`, generated by
`generate-chacha-scalar.py` from `chacha-riscv.pl` at a pinned commit, with
the Zbb rotations replaced by XTheadBb `th.srriw`). The stock C code and the
Zbb/RVV 1.0 kernels are not used: the C906 has neither extension.

That is where the vector code wins: per call, 128 bytes take 2469 ns with
the scalar code and 3427 ns as one padded vector group, 192 bytes 3703 ns and
3508 ns.

GHASH uses 8-bit tables, see "GHASH" below.

There is no run-time check: NanoKVM OS runs only on the SG2002, and its kernel
keeps the vector unit on for every user thread
(`platform/kernel/0078-riscv-user-vector-always-on.patch`: no thread can turn
it off or start a program with it off). The ChaCha20, GHASH and Poly1305 paths
therefore make no system call and need no environment variable, so they work
in every process, including those under seccomp filters (OpenSSH's
pre-authentication sandbox). CI does not run this library: it checks the
patches, the generated assembly and the arithmetic of the C906 kernels in
separate test programs.

`NKOS_CHACHA_TEST` adds an atomic counter at the actual assembly entry and an
accessor for a private test-library export map. Production builds omit both
and retain the original 5808 dynamic definitions.

The assembly is used under its BSD-3-Clause option; the runtime carries the
BSD license alongside OpenSSL's Apache-2.0 license. The new C glue is Apache-2.0.
Generate/verify with the same binutils used to build the firmware:

```sh
python3 firmware/crypto/openssl-c906/generate-chacha.py \
  --binutils /path/to/riscv64-buildroot-linux-musl- --check
```

## GHASH

`0010-ghash-c906.patch` replaces the 4-bit table GHASH (26 MB/s on the C906)
by the 8-bit table code of `firmware/cpu/go-crypto-c906/gen_ghash_table.py`
(two tables of 4 KiB per key, 114 MB/s; not constant-time, like the 4-bit
table). Both the block function and the single multiplication of
`CRYPTO_gcm128_*` use it.

Building the tables costs about 9 us, as much as hashing 300 bytes with the
4-bit table. A key therefore hashes its first 512 bytes with the 4-bit table
and builds the tables after that. They are the last member of
`GCM128_CONTEXT`, and `CRYPTO_gcm128_init` zeroes only the members before
them.

With TLS-like records (one key, a new IV, 13 bytes of AAD and a tag per
record; `openssl speed -aead` sets the key again for every record and does not
show this), a 1400-byte AES-128-GCM record encrypts in 44 us, against 80 us
with the 4-bit table and without the function order below. Records that set
the key every time are about 1 us slower up to 256 bytes (the larger context).

## Function order

The C906 has a 2-way 32 KiB instruction cache and no L2 cache. OpenSSL's hot
functions are spread over a 2 MiB text segment, and the ones a TLS record
calls evict each other depending on where unrelated code happens to move
them: the same 773 million instructions of a ChaCha20-Poly1305 record
benchmark took 1.16 or 1.30 billion cycles in two builds that differed only
in the GHASH code, with 1.2 and 2.0 million instruction-cache misses (about
170 cycles each).

`scripts/build-openssl.py` therefore compiles with `-ffunction-sections` and
links with `--section-ordering-file=hot-sections.ld`. The file lists the
assembly kernels and about 620 C functions of libcrypto and libssl by workload
class, so that the code one workload touches is contiguous: functions common
to several classes, ChaCha20-Poly1305 records with the TLS record path,
AES-GCM records, SHA-256, the other hashes, TLS connections. After the build
the script checks that nearly all listed names are still functions and close
together; a new OpenSSL version that renames or inlines them fails the build
instead of silently losing the order.

With the order, a 1400-byte ChaCha20-Poly1305 record takes 24.6 us instead of
28.5 us, and a 16-byte SHA-1 digest 1-4 instruction-cache misses instead of
13-21. The address of libc relative to libcrypto changes from run to run and
still moves a record by about 0.5 us.

The build also passes
`-falign-functions=4 -falign-jumps=4 -falign-loops=4 -falign-labels=4`
(`scripts/nanokvm_cpu_profile.py`): without these flags a 16-byte SHA-256
digest (4300 instructions over about a hundred functions) takes 27-31
instruction-cache misses instead of 10. After a change of OpenSSL, of the
patches or of the flags, measure records and small digests again.

To regenerate `hot-sections.ld`:

1. Build OpenSSL with `-finstrument-functions
   -finstrument-functions-exclude-file-list=test/,include/openssl/`,
   `no-tests`, and `hot-sections/hooks.c` compiled into `LDFLAGS`.
2. On a device, run each workload with `LD_PRELOAD=callcount.so`
   (`hot-sections/callcount.c`, built with `-pthread`; it counts the calls of
   all threads and writes "module offset count" lines to `$CYG_OUT.<pid>`):
   `openssl speed -bytes 1400 -aead` of
   chacha20-poly1305 and aes-128-gcm, encryption (`chacha.txt`, `gcm.txt`) and
   `-decrypt` (`chachad.txt`, `gcmd.txt`); `openssl speed -evp` of sha256 and
   `-hmac sha256` (`hash1.txt`, `hash2.txt`), of sha1, sha512, md5, sha3-256
   and shake128 (`hash3.txt` to `hash6.txt`, `hash9.txt`); ML-KEM-768
   (`kem.txt`); an `openssl s_server` with a P-256 certificate taking TLS 1.3
   handshakes with X25519MLKEM768 and ChaCha20-Poly1305 (`tls1.txt`); and the
   web server itself, its counts cleared with SIGUSR1 and written with SIGUSR2
   around 200 new connections (`shs.txt`) and around tens of MB over one
   connection (`srec.txt`). A signal only queues the request: start the load
   after `cleared N` in `$CYG_OUT.<pid>.state` has grown, and read the profile
   after `written M` has grown. A completed empty sample leaves no profile
   file. If writing fails, the counter stays at its previous value.
3. Turn each output into "calls symbol" lines with `nm` of the instrumented
   libraries and run `hot-sections/mkorder.py OUT BUILD READELF PROFILES`,
   with `BUILD` the tree of a normal build and `PROFILES` the directory
   holding them. It stops without writing `OUT` when one of the profiles
   named above is missing or names no function of the build.

The instrumented build counts functions the normal build inlines, so
`mkorder.py` keeps only names that have a section of their own in `BUILD`
(the code of libcrypto and libssl and of the providers built into libcrypto).
After the build, nearly all listed names must still be functions of the two
libraries.

The list from these profiles, against the one before it (three alternated
runs each, same patches): AES-128-GCM records +11 %, ChaCha20-Poly1305 records
the same; 64-byte digests SHA-256 +7 %, HMAC-SHA-256 +6 %, SHA-1 +104 %,
SHA-512 +56 %, SHA3-256 +36 %, MD5 +27 %; ML-KEM-768 key generation +10 %,
encapsulation +9 %, decapsulation +4 %; P-256 signatures and X25519 the same.
The web server's CPU for new TLS connections and for downloads shows no
measurable change. A quarter of the names of the list before were no longer functions
(inlined or renamed).

## NIST curves

The build enables `enable-ec_nistp_64_gcc_128`: OpenSSL has no RISC-V
assembly for P-256 and otherwise uses its generic big-number code. On the
SG2002 an ECDSA P-256 signature takes 1.8 ms with it and 13.8 ms without.

## Direct SG2002 transport

`0002-hwcrypto-transport.patch` adds the shared private ioctl client for subsequent
per-algorithm patches. On its own it selects no hardware algorithm and changes
no EVP result. It is compiled only for RISC-V64, outside the FIPS module. The
module ships in the same image, so there is no ABI or capability probe; a
process keeps one descriptor for all threads. EIO/ETIMEDOUT from a poisoned or
hung engine still fall back to software.

## SHA-224/256

`0003-sha256-dma.patch` uses the shared direct transport for full compression
chunks. OpenSSL owns streaming, padding, digest lengths and software fallback.
The FIPS module is excluded. The remainder goes straight to the scalar C906
kernel; the Zvknh check of the stock dispatch is not compiled for XTheadBb
builds. `tests/test-scalar.py` runs the patched wrapper and scalar assembly on
QEMU's C906 CPU. DMA starts at 1 KiB (wall-clock break-even).

The scalar kernels come from `firmware/cpu/go-crypto-c906/gen_sha2_c906.py`:
SHA-256 (`sha256-c906.S`) and SHA-512 (`sha512-c906.S`, also SHA-384 and
SHA-512/256). Rounds 0 to 15 are emitted once and one body of 16 rounds runs
three (SHA-256) or four (SHA-512) times, 4.5 KiB of code each. A loaded value
is used no sooner than two instructions later; w[i-1], w[i-2] and w[i-16]
stay in registers. On the SG2002: SHA-256 2451 ns per block (26.1 MB/s);
SHA-512 3103 ns per block against 4240 for C (41.2 against 30.2 MB/s in the
same test program). The generator checks itself against a plain
implementation anchored to hashlib.

## AES

`0005-aes-c906.patch` separately optimizes the existing scalar AES table lookups
with XTheadBb byte extraction and scaled XTheadMemIdx loads. The original
RISC-V/FIPS assembly remains the fallback. It changes neither tables nor key
schedules.

`0005-aes-dma.patch` adds ECB/CBC/CTR and the AES-CTR primitive used by GCM.
OpenSSL retains streaming, padding, GHASH, authentication and TLS handling.
The shared block helper commits only completed chunks and supports separate
full-width and GCM counters. GCM installs the AES-CTR callback for every record;
below the 512-byte DMA minimum it encrypts one AES block per call with 64-bit XOR
and a register counter.

ECB, CBC and CTR hand the driver up to 64 KiB per `HWCRYPTO_RUN` (its
buffers); the AES-CTR callback of GCM stays at 4 KiB. With 64 KiB per RUN,
`openssl speed -elapsed` encrypts 64 KiB with AES-128-CBC at 196 MB/s, against
105 MB/s with 4 KiB per RUN.

A RUN in place of up to 4 KiB goes through a stack scratch, so that a late
failure leaves the input for the software fallback. A longer one goes to the
driver as it is; if the driver answers EIO or ETIMEDOUT (its engine is lost
until the reboot) the cipher operation fails instead of continuing in software,
because a driver that works on the caller's pages may have written part of the
output. `HWCRYPTO_GCM` in place is treated the same way.

From 4 KiB, a GCM update hands its whole blocks to the driver's
`HWCRYPTO_GCM` ioctl instead (the driver's ABI header is copied into
`0002`). The driver runs AES-CTR on the engine in 4 KiB chunks and, while
each chunk runs, the kernel's C906 GHASH over the previous chunk's
ciphertext (encryption) or the same chunk's input (decryption), as its
`gcm(aes)` does. The request carries the key, H, the GHASH accumulator Xi and
the counter block, and the driver returns Xi and the counter advanced over the
completed prefix. As for `AES_GCM_ASM`, `CRYPTO_gcm128` first finishes the
associated data and any partial block, and keeps the lengths, the last partial
block and the tag. If a call fails or stops early, the rest takes the CTR
callback path. One call costs about 2.4 us more than `HWCRYPTO_RUN`, and
below 4 KiB the overlap does not pay for it: 512 to 1400-byte records are
about 10 us slower with the limit at 512 bytes. With `HWCRYPTO_GCM`,
`openssl speed -elapsed -evp` encrypts 16 KiB with AES-128-GCM at 64-65 MB/s,
against 46-47 MB/s on the CTR callback path.

The engine is shared with the server's SRTP and with OpenVPN data channel
offload, which uses it from softirq.

A driver without `HWCRYPTO_GCM` answers ENOTTY: after an update the module of
the running kernel is older than the library until the reboot. The library
remembers that and keeps the AES-CTR path.

`0004-sha1-dma.patch` sends the whole blocks of SHA-1 to the engine as
`0003` does for SHA-256, from 2 KiB (at 1 KiB the C code is faster: 46 MB/s
against 34). Both hand the driver up to 64 KiB per request; SHA-1 of 64 KiB
runs at 196 MB/s on the engine, against 57 MB/s in C.

DES, TDES and SM4 OpenSSL offloads are not included. The AES helper rejects
other algorithm IDs, and the legacy provider does not link the SG2002
transport.

## Poly1305

Upstream OpenSSL 3.5 has no RISC-V Poly1305 assembly and runs the generic C code.
`0011-poly1305-riscv.patch` adds `crypto/poly1305/asm/poly1305-riscv.pl`
from CRYPTOGAMS (Andy Polyakov, written for OpenSSL's `poly1305_init`,
`poly1305_blocks`, `poly1305_emit` interface), byte for byte the file Linux
7.3.1 builds for `lib/crypto` (SHA-256 `9a75fc04cd61e8fb...`), so OpenSSL
and the kernel run the same Poly1305. It is used under its BSD-3-Clause
option; the runtime carries `CRYPTOGAMS-BSD-3-Clause.txt`. `build.info`
selects it for `riscv64` like the other architectures' assembly; it is
outside the FIPS module, and the dynamic symbol table is unchanged (5808
definitions). The OpenSSL flags include `-mtune=thead-c906`, for which GCC
defines `__riscv_misaligned_fast`, so the word-load input paths are built
(no byte loads in `poly1305-riscv.o`).

With the C906 ChaCha20, `openssl speed -evp chacha20-poly1305` runs at
62.4 MB/s at 16 KiB with CRYPTOGAMS Poly1305 and 56.8 MB/s with the generic
one. OpenSSL's `test_poly1305` and an EVP check of 408 AEAD known answers and
rejected tags pass on the device.

### Vector Poly1305

`0012-poly1305-c906.patch` adds the C906 vector Poly1305 that the kernel and
the RustDesk add-on use too: radix 2^26, four blocks in XTheadVector lanes and
one in scalar registers per group of five. It is
`firmware/cpu/go-crypto-c906/gen_poly1305_vector.py --openssl`, and that
generator executes it against a big-integer Poly1305; see
`firmware/cpu/go-crypto-c906/README.md`.

- **Selection.** As for ChaCha20 and GHASH there is no run-time check (the
  kernel keeps the vector unit on for every user thread, patch 0078):
  `Poly1305_Init` replaces `func.blocks` with `ossl_poly1305_blocks_c906`.
- **Split.** The vector function takes runs of at least eight whole groups
  (640 bytes) with padbit 1. Cryptogams `poly1305_blocks` takes the rest and
  every other call.
- **Context.** The glue converts the Cryptogams context (h0, h1, h2; r0, r1,
  s1) to 26-bit limbs and back, after folding h2 as `poly1305_emit` does.
- **Threshold.** The vector function computes r^2..r^5 on every call, so
  with `EVP_MAC`, a fresh key per message, it overtakes Cryptogams at about
  640 bytes. At 16 KiB it hashes at 294-310 MB/s, against 194-200 for
  Cryptogams.

The vector path produces the same tags as Cryptogams on 6000 cases (lengths
to 65 KB, offsets 0-15, update splits, all-ones keys and messages) and passes
the 408-case EVP AEAD check.

## SHA-3 and SHAKE (Keccak)

Upstream OpenSSL 3.5 has no RISC-V Keccak assembly and builds `keccak1600.c`. `0013-keccak-c906.patch` adds
`crypto/sha/keccak1600-c906.S`, generated by `generate-keccak.py` from CRYPTOGAMS `keccak1600-riscv.pl` (commit
`4acc4a308eab`, SHA-256 `4b3d783ff0c6...`, the latest; BSD-3-Clause option, the runtime already carries
`CRYPTOGAMS-BSD-3-Clause.txt`). The C906 has no Zbb, so the generator takes the no-Zbb path (all 25 lanes in
registers, lane complementing instead of `andn`) and fuses each shift/shift/or rotate of the round into one XTheadBb
`th.srri`, checking the data flow and liveness of every temporary: 29 per round. The output is preprocessed
assembly (misaligned-fast input, no Zicfilp). It provides `SHA3_absorb` and the permutation, renamed
`ossl_keccakf1600_c906` (hidden); OpenSSL's `SHA3_squeeze` takes a `next` argument the CRYPTOGAMS one lacks, so
`keccak1600_c906.c` is OpenSSL's squeeze on top of that permutation. `build.info` selects both for `riscv64`.

Regenerate or check the file in the patch:

    generate-keccak.py --print-url
    generate-keccak.py --cryptogams keccak1600-riscv.pl --binutils <riscv64 prefix> --check

On the device (`openssl speed`, 16 KiB): SHA3-256 27.6 to 33.0 MB/s, SHAKE128 34.1 to 41.0 MB/s; one permutation
takes 4.03 us. ML-KEM-768, which TLS 1.3 uses in its default key share, spends most of its time outside Keccak:
keygen 850 to 799 us, encapsulation 560 to 547 us, decapsulation 801 to 781 us. Checked on the device: the
permutation against a plain FIPS 202 reference on 20,000 random, all-zero and all-one states, three chained each
(and a build with one round constant changed fails it); SHA3-224/256/384/512 and SHAKE128/256 of 306 inputs from 0
to 65,537 bytes at several output lengths against another OpenSSL (5,508 values); ML-KEM-768 keys of each build
encapsulated by the other and decapsulated to the same secret.

## ML-KEM

OpenSSL 3.5's ML-KEM (`crypto/ml_kem/ml_kem.c`) computes its number theoretic transforms and base-case products one
16-bit coefficient at a time; they took about 40 % of a key generation. `0014-ml-kem-c906.patch` replaces
`scalar_ntt`, `scalar_inverse_ntt`, `scalar_mult` and `scalar_mult_add` on `riscv64` with XTheadVector code in
`crypto/ml_kem/ml_kem_c906.c` (`ML_KEM_C906`, set by `build.info`). The arithmetic is the scalar code's, so the
results are the same bits: products of reduced values in 32-bit lanes, the same Barrett step (`x * 5039 >> 24` as
the high half of a multiply by `5039 << 8`), `reduce_once` as an unsigned minimum with `x - q`. Layers with blocks
of 8 or more coefficients run along the block; in the last two layers, and in the products, the coefficients are
loaded as segments, so each block's even and odd halves land in separate registers next to a vector of its roots.
No branch or address depends on the data.

`ml_kem_c906.c` is RVV intrinsics, which GCC compiles to XTheadVector: the OpenSSL CPU profile includes
`xtheadvector` for it, while compiler vectorization and vector string operations stay off, so no other compiled C
function of OpenSSL contains vector instructions (checked on the built libraries).

On the device (`openssl speed`, microseconds for keygen / encapsulation / decapsulation):

| | ML-KEM-512 | ML-KEM-768 | ML-KEM-1024 |
|---|---|---|---|
| Keccak only | 539 / 399 / 556 | 801 / 554 / 780 | 1117 / 735 / 1035 |
| with this patch | 367 / 212 / 262 | 521 / 257 / 339 | 716 / 322 / 434 |

One transform takes 6.4 us instead of 38.8 us, the inverse 6.5 us instead of 35.7 us, a product with sum 2.1 us
instead of 7.5 us. Checked on the device: the four functions against the scalar ones on 200,000 random polynomials
and products (with the edge cases 0 and q-1); ML-KEM-512/768/1024 keys of each build encapsulated by the other and
decapsulated to the same secret; SHA-3/SHAKE digests unchanged. The patch moves unordered code (see Function order):
16-byte digests changed by -24 % (SHA-1) to +37 % (SHA-256), SHA3-256 by -14 %; ChaCha20-Poly1305 and AES-GCM
records and digests from 1 KiB on are unchanged.

## Argon2

NanoKVM-Server hashes passwords with OpenSSL's `ARGON2ID` KDF (19 MiB, 2 passes, 1 lane). Its compression function,
`fill_block` in `providers/implementations/kdfs/argon2.c`, copies and XORs whole 1 KiB blocks four times and runs the
BlaMka permutations on words addressed through pointers into a block on the stack: on the C906 the loads and stores
took most of the time, not the arithmetic (16 permutations alone take 4.6 us, the function 8.5-9.5 us).
`0015-argon2-fill-block.patch` keeps the 16 words of each permutation in registers with constant offsets, reads
`ref ^ prev` straight from the input blocks in the column permutations, and writes `next` in one sequential pass at
the end. Writing `next` from the row permutations instead saves another pass in the cache but loses it all again over
19 MiB: the stride-128 stores miss in a worse order. The results are the same; `ref` and `next` may be the same
block (`next_addresses`), and every word of `next` is written after the last read of `ref`.

On the device: `fill_block` 8.5 to 6.4 us in the cache; over the server's 19 MiB one pass takes 180 ms instead of
215 ms, and a whole hash about 500 ms instead of 550 ms. The rest is fixed: the first pass writes 19 MiB of fresh
memory, about 115 ms more than a later one, mostly page faults (the kernel has no transparent huge pages). Checked
on the device: Argon2id, Argon2i and Argon2d with 1, 2 and 4 lanes, 1 to 3 passes and 32 KiB to 1 MiB of memory
(108 sets), and the server's parameters, give the same key as the build without the patch; 20,000 blocks with and
without XOR and 2,000 with `ref` and `next` the same block equal the reference function.

`0016-argon2-worker-cleanup.patch` is OpenSSL's own fix from its 3.5 branch, after 3.5.9 (commit `5a9068ccd9`):
after a failure the threaded fill joins only the workers still outstanding, and the memory of the hash is freed.
The memory of a hash is not mapped with 2 MiB pages: with transparent huge pages a hash took about 110 ms less,
but the huge-page code in the kernel's fault path makes every anonymous page fault of every process
slower (20.8 µs instead of 18.8 µs), and without them a mapping of its own saves nothing over OpenSSL's allocation.
