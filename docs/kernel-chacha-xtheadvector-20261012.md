# XTheadVector ChaCha in the kernel — 2026-10-12

Linux `7.2.10-nanokvm-os-r2` adds an XTheadVector backend to `lib/crypto`'s
ChaCha (`platform/kernel/0040-crypto-riscv-xtheadvector-chacha.patch`). Every
in-kernel ChaCha user goes through it: WireGuard (and NetBird in kernel
mode), ChaCha20-Poly1305 and XChaCha through the library, the `chacha20`
skcipher and the `rfc7539` AEAD of the crypto API (IPsec ESP, for example).
Userspace VPNs are not affected: Tailscale's wireguard-go and OpenVPN do their
own crypto.

## What changes

- `lib/crypto/riscv/chacha-riscv64-xtheadvector.S`, generated by
  `firmware/cpu/go-crypto-c906/gen_chacha_linux.py`: the same five-block kernel
  as the Go one (four blocks in vector lanes, a fifth in scalar registers,
  interleaved), in the kernel's calling convention, any even round count
  (ChaCha20 and ChaCha12), the counter advanced in the state, the key stream
  wiped from the stack.
- `lib/crypto/riscv/chacha.h`: the backend is enabled at boot when
  `has_xtheadvector()` and VLEN >= 128. A message of at least 129 bytes from
  a context where `crypto_simd_usable()` (process context and softirq, so
  WireGuard's receive path too) runs between `kernel_vector_begin()` and
  `kernel_vector_end()`; a remainder below a group runs as one more group in a
  stack buffer. Shorter messages and contexts without kernel-mode vector use
  the generic code. The Zvkb backend keeps its previous conditions.
- `CRYPTO_LIB_CHACHA_ARCH` defaults to y with `RISCV_ISA_XTHEADVECTOR`;
  `platform/kernel/config` gains that line, and the release becomes `r2`
  (`CONFIG_LOCALVERSION`, `build.sh`).

The vector state handling it relies on is in patches 0032, 0034 and 0035.
`HChaCha` stays generic. Poly1305 stays the existing scalar RISC-V assembly
(`CRYPTO_LIB_POLY1305_ARCH=y`): measured below at 211–224 MB/s, it is not the
limit, and a 64-bit vector datapath gives no multiply throughput over the
scalar `mul`/`mulhu`.

## Device qualification

`firmware/cpu/go-crypto-c906/linux-test/` builds a module against the running
kernel that carries the same assembly and glue. On the stand (SG2002 C906,
`7.2.10-nanokvm-os-r1`, idle video), loading it:

- RFC 8439 2.4.2 vector: ok.
- Against `chacha_block_generic()`, output and final state identical in all
  cases: 20,000 random cases of the vector glue in process context and 5,000
  with bottom halves disabled; 10,000 and 5,000 through `chacha_crypt()`.
  Lengths 1–4096, source and destination offsets 0–63, in place and out of
  place, ChaCha20 and ChaCha12, counters across the 32-bit wrap.
- Preemption inside the vector section: a kernel thread that never yields
  competes with a thread encrypting 64 KiB per call (about 0.7 ms, nearly all
  of it in the assembly), each result compared with a precomputed reference,
  for 4 s: 1,429 calls, 238 involuntary context switches of that thread,
  0 mismatches; 3,000 random cases in the loading thread meanwhile, 0
  failures, 55 involuntary switches. No warning or oops in the log.

| bytes | generic MB/s | XTheadVector MB/s | Poly1305 MB/s |
| ---: | ---: | ---: | ---: |
| 64 | 41 | 15 | 120 |
| 128 | 42 | 32 | 163 |
| 129 | 29 | 32 | 129 |
| 192 | 43 | 47 | 182 |
| 320 | 42 | 86 | 207 |
| 1420 (WireGuard packet) | 42 | 81 | 235 |
| 4096 | 43 | 92 | 248 |
| 16384 | 43 | 93 | 249 |

Wall time, 300 ms per cell, the final run; an earlier run the same day
measured all three columns about 10% lower (37 / 73 / 211 MB/s at 1420
bytes), the ratio was the same. From 129 bytes the vector path is ahead;
below it stays generic. With ChaCha20 at about twice the generic rate and
Poly1305 at 235 MB/s, ChaCha20-Poly1305 on a 1420-byte packet goes from about
36 to about 60 MB/s of crypto per core.

## Build

`build.sh kernel modules initramfs boot tools verify` with the pinned
toolchain: the Image, the 25 FIT variants with their hashes and
`kernel.release` change, and all 82 modules change their version string
(`lib/modules/7.2.10-nanokvm-os-r2`); `expected.sha256` is updated for exactly
those 136 entries. Device trees, initramfs and tools are unchanged.

## Not covered

- The module qualification ran on the r1 kernel with the backend loaded as a
  module; the r2 Image itself was not booted on the stand, and no WireGuard
  throughput was measured end to end.
- XTheadVector is not emulated by QEMU; there is no CI execution of the
  vector code, only the generator's encoding check.
