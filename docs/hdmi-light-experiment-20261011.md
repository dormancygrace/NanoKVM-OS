# Эксперимент HDMI light: первый результат

11 октября 2026. Ветка `codex/scpcom-evaluation-20261011`, базовый NanoKVM OS `1524f5e69963419c01c72e5a8af783ffcb1612aa`.

Подготовлен отдельный профиль сборки `hdmi-light`. На текущем наборе исходников он уменьшил комплект медиа-библиотек **с 2 059 328 до 1 225 104 байт: −834 224 байта, или 40,51%**. Вместо 19 файлов получается 6. Оба размера получены после одинакового `strip --strip-unneeded`; системные libc/libstdc++/libgcc_s и VPU firmware в эту сумму не входят и остаются необходимыми. Это экономия размера ELF-файлов, не измерение RAM, сжатого образа, CPU или FPS.

## Что изменилось

Первый шаг сохраняет имеющийся путь обработки HDMI, регистрацию сенсора, ISP init/run, загрузку tuning BIN и алгоритмы. Открытые MPI-компоненты связываются из текущих статических архивов внутри `libkvm_mmf.so`. Линкер удаляет недостижимые секции, а внутренние sample/MPI-функции перестают экспортироваться как общий API.

Сохранены все **48 реально существующих MMF-символов** базовой сборки, включая C++ и `extern "C"` функции. Дополнительно экспортируются 23 символа, нужные vendor-библиотекам для обратных вызовов и доступа к общим данным, и 7 символов конфигурационного probe. Проверяются точный набор экспортов, DT_NEEDED и разрешение всех обязательных ELF-ссылок.

`libae.so`, `libawb.so`, `libaf.so`, `libisp_algo.so` остаются отдельными и используют прежние алгоритмы. Попытка включить их старые GCC10-объекты в общий ELF выявила конфликт атрибутов legacy vector и GCC16 `xtheadvector`. Атрибуты не переписывались, проверки линкера не отключались. Границы DSO сохраняют существующий подход к совместимости этих объектов.

Итоговый комплект:

| Файл | Байты |
|---|---:|
| libkvm_mmf.so | 794848 |
| libkvm.so | 67872 |
| libae.so | 130944 |
| libawb.so | 51456 |
| libaf.so | 43064 |
| libisp_algo.so | 136920 |
| **Всего** | **1225104** |

Dummy-функций, зависимости от малого ядра и изменений алгоритмов здесь нет. Название HDMI light относится к уже существующему LT6911-набору исходников MMF. Это первый этап уменьшения набора библиотек; отключение AE/AWB и других вычислений в него не входит.

## Изменения в репозитории

- `scripts/build-enhanced-mmf.py`: выбор `NANOKVM_MMF_PROFILE=full|hdmi-light`; по умолчанию full.
- `scripts/nanokvm_mmf_link.py`: компактная линковка, сохранение MMF API и vendor callbacks, проверка ELF-зависимостей.
- `scripts/build-hdmi-light.py`: сборка MMF/capture и отдельного комплекта с хешами, размерами и уведомлениями о лицензиях.
- `scripts/test-mmf-light-link.py`: проверки C/C++ API, отказа при пустом API и обнаружения неразрешённых сильных ссылок.
- `firmware/probes/mmf-light-load.c`: проверка загрузки и наличия API без обращения к аппаратуре.
- `platform/build.sh`: явно использует full для обычной производственной сборки. Существующий пакет из 19 библиотек не превращается случайно в смешанный комплект при унаследованной переменной окружения.

## Проверено

1. Обе конфигурации MMF собраны текущим GCC16.2 с действующим CPU profile; действующие предупреждения и `-Werror` сохранены. Библиотека capture успешно связана с light MMF через `-z defs`.
2. Все 48 существующих функций MMF присутствуют в обеих сборках. Внутренний набор экспортов light проверен точно, включая 23 vendor callbacks.
3. Полный комплект light проходит проверку зависимостей, включая обратные ссылки из vendor DSO. Отрицательная проверка с отсутствующей `libaf.so` корректно завершается ошибкой.
4. Три host-теста границы линковки проходят. Проверки синтаксиса Python, shell и пробелов проходят.
5. В QEMU 8.2.2 выполнены `dlopen("libkvm.so", RTLD_NOW)` и `dlsym` всех 48 функций для baseline и light: PASS. Вариант light использовал только свой комплект медиа-библиотек и системные библиотеки, без подхватывания прежних MPI DSO.
6. Полный `mmf-config-probe` в QEMU получил SIGILL на одной и той же векторной инструкции `vsetvli` в начале `main` для обеих конфигураций. Этот тест **не считается пройденным**. Проверка загрузки использует отдельный scalar rv64gc runner; производственные библиотеки и CPU profile не перекомпилировались под эмулятор.

Аппаратная проверка видео и оценка производительности не выполнялись. Успешная загрузка подтверждает совместимость символов, но не эквивалентность поведения всех аппаратных путей.

## Воспроизведение

Используются подготовленные текущим platform builder исходники и библиотеки из `platform/sources.lock`. Данный эксперимент повторно использовал существующий подготовленный кеш; это не чистая пересборка всего release.

В WSL, из корня репозитория, с новым каталогом результата:

```bash
export NANOKVM_MPI_SOURCE=/path/to/platform/native/src/cvi_mpi
export NANOKVM_SENSOR_SOURCE=/path/to/platform/native/src/sensors
export NANOKVM_INIH_SOURCE=/path/to/platform/native/src/inih
export NANOKVM_MPI_THIRDPARTY_OUTPUT=/path/to/platform/native/bin
export NANOKVM_BUILDROOT_OUTPUT=/path/to/platform/buildroot-output
export NANOKVM_HDMI_LIGHT_OUTPUT=/path/to/new/hdmi-light
python3 scripts/test-mmf-light-link.py
python3 scripts/build-hdmi-light.py
```

Скрипт создаёт `dl_lib/`, `manifest.json`, `mmf/link-profile.json`, карту линковки, probe и notices. Он отклоняет непустой каталог результата и не устанавливает файлы на устройство. В архиве эксперимента сохранены хеши статических архивов и vendor DSO, логи и точные параметры проверки.

Для загрузочного smoke test runner собирается отдельно с `-march=rv64gc -mabi=lp64d -O0`, а список символов берётся из `mmf/link-profile.json`. Сам тест ничего не инициализирует через MMF.

## Следующий проверяемый шаг

В согласованное окно на NanoKVM проверить этот комплект как единое целое: холодный старт, видео, отсутствие/возврат HDMI, смену разрешения, H.264/MJPEG, оба типа LT6911, работу tuning BIN и повторный start/stop. Сравнить FPS, задержку, CPU и RSS/PSS на одинаковом источнике. Host-копии для восстановления достаточно; резервные копии на устройстве не создавать.

Компактная библиотека локализует внутренние MPI-символы, поэтому сторонние ISP/PQ-плагины, рассчитывающие на весь прежний экспорт, требуют отдельной проверки. Нельзя проверять этот результат наложением на уже работающий процесс с загруженными старыми DSO: нужно завершить процесс и использовать согласованный полный набор библиотек.

Если аппаратное поведение совпадёт, следующий эксперимент — обоснованное отключение конкретных алгоритмов для YUV с сохранением обязательного ISP lifecycle. Текущий выигрыш уже получен без такого изменения поведения.
